The star

Both dimensions join directly to both facts. There is no intermediate table anywhere in the model, which is what makes it a star rather than a snowflake: every question the dashboard asks is one join away from the measures.

Dimension Fact PK primary key · FK foreign key

WHY THE INDEX LIVES INSIDE dim_ticker

SPY is not a separate table. It sits in dim_ticker alongside the 118 trusts, separated only by entity_type. That one decision is what makes the star work: comparing a trust against the S&P 500 becomes a self-join on one fact table rather than a union of two, and both sides are guaranteed to have been measured by the same code.

How an SCD2 version reaches a fact row

A trust changes manager. dim_ticker closes the old row and opens a new one, so the same ticker now has two surrogate keys. The question a reviewer always asks next is which one a fact row carries — and the answer differs between the two facts, on purpose.

What a snowflake would have cost

The obvious-looking move is a dim_manager table. It was considered and rejected, and the drawing shows why — it adds two hops and a bridge table to reach the same measures.

Considered and rejected

dim_manager
Many-to-many with tickers, needing a bridge table that fans measures out. The full comma-separated manager list is kept on dim_ticker, so no names are lost.
dim_management_group
It has no attributes of its own. A table would snowflake the model for nothing — beat rate by group is a GROUP BY.
rank_band
Dropped entirely. It existed only because manager data was unavailable, and it dragged the heaviest piece of the old design along with it: a monthly ranking recompute.
a degenerate dimension
There isn’t one. entity_type is a plain column, and a degenerate dimension is normally a transaction ID — this model has no natural transaction ID, so the term would be misapplied rather than clever.
