One fact, four dimensions and one bridge — the model behind “what share of UK investment trusts beat the S&P 500?”

The star, and the one hop in it

Three dimensions join the fact directly. dim_manager does not: it reaches the fact through bridge_ticker_manager, because a trust has several managers and a manager can have several trusts. That one hop means this is not a pure star — it is the price of modelling a genuine many-to-many honestly, and it is stated here rather than glossed.

Dimension Fact PK primary key · FK foreign key

WHY THE INDEX LIVES INSIDE dim_ticker

SPY is not a separate table. It sits in dim_ticker alongside the 118 trusts, separated only by entity_type. That one decision is what makes the star work: comparing a trust against the S&P 500 becomes a self-join on one fact table rather than a union of two, and both sides are guaranteed to have been measured by the same code.

How an SCD2 version reaches a fact row

A trust changes manager. dim_ticker closes the old row and opens a new one, so the same ticker now has two surrogate keys. The question a reviewer always asks next is which one carries downstream — and since the monthly fact was retired, the answer is the bridge. bridge_ticker_manager is keyed on the versioned ticker_key, so it is the one table that reads the history.

Why the bridge earns its place

A bridge table is not free: it adds a hop and it fans measures out. It is worth it only when the relationship is genuinely many-to-many in both directions, and here it is. The drawing shows the two grains that were rejected and the one that was built.

THE FAN-OUT, AND HOW IT IS HANDLED

A bridge means a trust with twelve managers is counted twelve times. That is not always wrong, but it is always a choice, so the bridge carries allocation_factor — one over the manager count — and the semantic layer names which basis it uses:

Impact ignores the factor, so a trust counts once for each of its managers. Right for “what share of managers had a trust that beat the index”. Allocated weights by it, so the weights sum to one per trust and the total still reconciles to the 440 rows in the fact. v_beat_rate_by_cut uses impact, and says so in a comment.

Considered and rejected

dim_manager on the manager list
One row per comma-separated list rather than per person. Every trust’s list is unique, so it would have been 97 rows for 97 trusts — dim_ticker under another name. The individual grain was built instead.
lead manager only
Would have avoided the bridge entirely by keeping just the first name. Rejected because the source never says who leads — the order is the order it was written in, and treating it as seniority would be inventing data.
the monthly fact
Retired at step 13. It had exactly one consumer and no view or dashboard tile read it, so the horizon fact reads silver.monthly_performance directly and Gold holds one fact at one grain.
rank_band
Dropped entirely. It existed only because manager data was unavailable, and it dragged the heaviest piece of the old design along with it: a monthly ranking recompute.
a degenerate dimension
There isn’t one. entity_type is a plain column, and a degenerate dimension is normally a transaction ID — this model has no natural transaction ID, so the term would be misapplied rather than clever.
